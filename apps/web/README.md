# @canvas/web — редактор нод на React Flow

React + TypeScript + Vite + `@xyflow/react`. Цепочка «текст → генератор →
результат», сохранение графа через REST с debounce и последовательной очередью,
оптимистичная блокировка по `ETag`, тестовая генерация изображения с опросом,
идемпотентностью и защитой от гонок.

## Запуск

Требуются Node.js 24.x и npm 11.x (см. корневой `README.md`). Из свежего клона:

```sh
npm ci                       # ставит зависимости всех воркспейсов, включая apps/web

# 1) API (порт 4001) — в одном терминале:
npm run dev                  # из корня репозитория: собирает contracts и поднимает API

# 2) Фронтенд (порт 5174) — в другом терминале:
npm run dev -w @canvas/web
```

Откройте <http://localhost:5174>. Пространство создаётся автоматически и
переоткрывается после перезагрузки.

Сборка и проверка типов:

```sh
npm run build -w @canvas/web        # tsc --noEmit + vite build
npm run typecheck -w @canvas/web
```

Другой порт API: `VITE_API_URL=http://localhost:4101 npm run dev -w @canvas/web`.

> Типы API берутся из `packages/contracts` через tsconfig `paths` — отдельная сборка
> contracts для фронтенда не нужна.

## Архитектура

```
src/
  api/
    http.ts        единственное место с fetch: базовый URL, заголовки, JSON,
                   проверка статуса, пустой ответ (204/304), разбор ошибок,
                   rawBody для точной отправки сериализованного графа
    errors.ts      ApiError — один вид ошибки (network | http | parse)
    endpoints.ts   типизированный каталог; graph.get/save отдают ETag явно
  lib/
    graph.ts       модель графа: типы нод, createNode, toPersistentGraph (горячий
                   путь), fromPersistentGraph, canConnect (валидация связей)
    poll.ts        общий опрос с отменой + Retry-After
    idempotency.ts newIdempotencyKey
    persist.ts     spaceId в localStorage (переоткрытие того же пространства)
  features/
    graph/
      SaveController.ts   debounce + последовательная очередь PUT + ETag + 412
      useGraphEditor.ts   ноды/связи/viewport, CRUD, onConnect, isValidConnection
      runtime.ts          контекст для нод (действия + рантайм-состояние генераций)
      nodes.tsx           PromptNode, GeneratorNode, ResultNode
      CanvasEditor.tsx    тулбар, статус сохранения, баннер конфликта, ReactFlow
    generation/
      useGenerations.ts   жизненный цикл генерации: idempotency, опрос, гонки, restore
```

**Слой API.** Компоненты не знают о HTTP. `http.request` централизует URL, заголовки,
сериализацию, статусы, пустые ответы и приведение ошибок к `ApiError`. У ответов
canvas нет обёртки — данные возвращаются напрямую. Заголовки, важные для контракта
(`ETag`, `Retry-After`, `Location`), доступны через возвращаемый `Response`.
`graph.save` отправляет **ту же строку**, что мы диффали (`rawBody`), с `If-Match`.

**Разделение persistent vs runtime.** В граф сохраняются только контрактные поля
(`id, type, position, data`). Служебные поля React Flow (`selected`, `dragging`,
`measured`, размеры) и рантайм-результаты генерации в persistent-данные не попадают:
`toPersistentGraph` проецирует ноды в контрактную форму. Картинка результата хранится
не в ноде (её схема этого не допускает), а в рантайм-состоянии генераций и
восстанавливается из списка генераций.

**Debounce и очередь сохранений (`SaveController`).** Любая правка вызывает
`schedule()` → debounce 500 мс → сохранение последнего состояния. Инвариант очереди:
никогда не два PUT одного графа параллельно. Правки во время активного PUT ждут; после
ответа контроллер сравнивает текущий граф с сохранённым и при отличии сохраняет ещё раз
с новым `ETag`. Так более свежее состояние не теряется, а порядок строго
последовательный.

**Конфликт `ETag` (412).** `PUT` шлёт `If-Match` с текущим `ETag`; ответ даёт новый.
При `412` контроллер переходит в состояние конфликта: локальный черновик сохраняется,
автосохранение останавливается, показывается баннер, пользователь явно перечитывает
серверную версию. Локальные правки автоматически не уничтожаются.

**Генерация.** По кнопке: `flush()` — дождаться сохранения последних правок и получить
актуальный `ETag`; при ошибке сохранения генерация не запускается. Затем `POST` с новым
`Idempotency-Key` и `graphETag`. При `202` — опрос по `pollIntervalMs` до `succeeded` /
`failed`. Успех показывает картинку в связанной ноде результата.

**Гонки генерации.** Каждая генерация идентифицируется `generationId`; на генератор —
один активный опрос с собственным `AbortController`. Перед применением результата
проверяется, что генерация не устарела (`generationId` совпадает с текущим для этой
ноды) и что нода результата ещё существует. Поэтому старый ответ не попадёт в чужую
ноду и не перезапишет более новую попытку. Удаление ноды отменяет её опрос.

**Идемпотентность и повтор.** Повтор после **сетевой** потери ответа переиспользует тот
же ключ (идемпотентный повтор). Новая генерация (после `failed`) получает новый ключ.
`409 GENERATION_IN_PROGRESS` разрешается подхватом активной генерации из списка.

**Опрос и отмена.** `poll()` останавливается при завершении, размонтировании и закрытии
пространства (общий cleanup отменяет все `AbortController`). Таймеры и слушатели не
утекают.

**Перезагрузка.** `spaceId` — в `localStorage`. При старте читаются пространство, граф и
список генераций; незавершённые генерации продолжают опрашиваться, готовые результаты
подставляются в ноды результата. Дубли генераций не создаются.

## Производительность — разбор одного участка

`lib/graph.ts → toPersistentGraph` — самый частый нетривиальный участок обработки:

```ts
const outNodes: GraphData['nodes'] = new Array(nodes.length);
for (let i = 0; i < nodes.length; i++) {
  const node = nodes[i]!;
  const position = { x: node.position.x, y: node.position.y };
  switch (node.type) {
    /* prompt → {text}, generator/result → {label} */
  }
}
```

- **Частота:** один раз на сохранение — после debounce 500 мс, а не на каждый кадр
  перетаскивания или нажатие клавиши.
- **Проходы/память:** по одному проходу по нодам и связям, оба выходных массива заранее
  заданного размера (`new Array(n)`) — нет растущего аккумулятора, нет промежуточных
  `map().filter()`, нет копий служебных полей. Проекция сразу в контрактную форму.
- **Ссылки (P2):** правка текста в `useGraphEditor.updateNodeText` заменяет объект только
  изменённой ноды (`prev.map(n => n.id === id ? {…n, data:{…n.data, text}} : n)`),
  остальные сохраняют ссылку — React Flow перерисовывает одну ноду. Рантайм-состояние
  генераций отдаётся через контекст, зависящий только от стабильных колбэков и двух
  `Map`, поэтому ввод текста не перерисовывает все ноды.

## Проверенные сценарии

Проверено вручную в браузере и подтверждено live-проверкой по HTTP (см. также
`npm run smoke`, проходит):

- Создание пространства и его переоткрытие после перезагрузки (без дублей).
- Добавление трёх типов нод (уникальные UUID), перемещение, редактирование текста.
- Связи только `текст → генератор` и `генератор → результат`; несовместимые типы, второй
  вход и второй выход генератора запрещены до создания связи.
- Удаление ноды удаляет её связи; сервер принимает оставшийся граф.
- Серия быстрых правок → одно сохранение после паузы 500 мс; одиночная правка тоже
  сохраняется.
- Медленный PUT + новые правки: PUT одного графа идут последовательно, свежие правки не
  теряются.
- `412`: локальный черновик сохранён, виден конфликт, доступно перечитывание сервера.
- Генерация: успех (картинка в ноде результата) и тестовый отказ (`SIMULATED_FAILURE`) с
  повтором.
- Гонка: изменение графа/повторный запуск во время генерации — старый результат не
  попадает в чужую ноду и не перезаписывает новую попытку.
- Удаление ноды во время генерации: опрос отменяется, результат не подставляется.
- Двойной клик по «Сгенерировать»: дублей нет (guard + `Idempotency-Key`).
- Перезагрузка во время генерации: опрос продолжается, дубль не создаётся.

## Известные ограничения

- Разрешение конфликта `412` — перечитывание серверной версии (сервер побеждает);
  трёхстороннего слияния нет (по заданию не требуется).
- Отдельное удаление связи без удаления ноды не выведено в UI (клавиша удаления
  отключена намеренно, чтобы не конфликтовать с редактированием текста); связи убираются
  вместе с нодой.
- Мобильная версия канваса не оценивается и не проектировалась.
- Тесты фронтенда не входят в задание; поведение проверялось вручную и через `smoke`.
